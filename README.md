# Resale Flat Prices Pipeline

Senior Data Engineer technical test — Part 1: an ETL pipeline over HDB resale flat
transaction data (Jan 2012 – Dec 2017), sourced programmatically from
[data.gov.sg](https://data.gov.sg/collections/189/view).

**Part 2** — the AWS data ingestion & exploitation architecture — is in
[`architecture/`](architecture/README.md): a PNG diagram built from the official AWS
Architecture Icons, plus the design rationale, requirement traceability, and trade-offs. The
diagram is generated by `python architecture/generate_diagram.py` and is reproducible from a
fresh clone.

## What this produces

Running the notebook end-to-end produces the five mandatory output datasets under `data/`:

| Output group | Folder | Description |
|---|---|---|
| Raw | `data/raw/` | The source CSVs exactly as published by data.gov.sg, plus a checksum manifest |
| Cleaned | `data/cleaned/` | Combined, in-scope, validated rows + remaining-lease + anomaly-flag columns |
| Transformed | `data/transformed/` | Cleaned + a unique plaintext `resale_identifier` column |
| Quarantined | `data/quarantined/` | Rows that failed validation or were exact duplicates, tagged with `quarantine_reason` |
| Hashed | `data/hashed/` | Cleaned columns + `hashed_identifier` only (plaintext identifier removed) |

The full write-up of findings, the quarantine-bucket breakdown, and documented assumptions
is in [`reports/data_profiling_report.md`](reports/data_profiling_report.md) (regenerated
each time the notebook runs).

## Setup

Requires Python 3.9+.

```bash
pip install -r requirements.txt
cp .env.example .env
# edit .env and set HASH_SECRET_KEY to any random string (used only locally, for the
# HMAC-based de-identification step — see src/deidentify.py for why a secret key matters)
```

## Running

```bash
jupyter notebook notebooks/hdb_resale_etl_pipeline.ipynb
```

Run all cells top to bottom. The notebook:
1. Discovers the datasets in data.gov.sg collection 189, keeps those whose published
   coverage overlaps Jan 2012 – Dec 2017, and streams any not already present into
   `data/raw/`. The raw files and their checksums (`data/raw/manifest.json`) are committed to
   this repo, so a fresh clone re-runs offline on exactly the same snapshot. Delete
   `data/raw/manifest.json` and the CSVs to pull the latest data from data.gov.sg instead.
2. Combines, profiles, validates/quarantines, computes remaining lease, flags anomalous
   prices, builds the Resale Identifier, de-identifies it, and writes all five output groups
   plus the profiling report.

Re-running is idempotent: cached raw files aren't re-downloaded, and every output CSV /
report is simply overwritten with the same result given the same inputs and `.env` key.

## Tests

```bash
pytest
```

48 unit tests cover the rule-bearing functions — source discovery and the combine guards, identifier construction (including the block
and month edge cases from the spec), the remaining-lease arithmetic, every validation rule,
the cleaned + quarantined = input invariant, the per-month completeness check, the anomaly heuristic, and the properties the
de-identification relies on (determinism, key-sensitivity, uniqueness). These are the places
where a silent error would flow into every output without the row counts ever looking wrong.

## Key design decisions (short version — full rationale in the profiling report)

- **No hardcoded sources**: datasets are discovered from collection 189 at run time and
  selected by their published coverage; rows are kept by their own `month`. The pipeline
  refuses to combine files that overlap in time (it would double-count), and pins raw files by
  SHA-256 so every re-run reproduces the same snapshot.
- **"Jan 2012 as strict authoritative set" is used two different ways**, deliberately: for
  the *schema* of the combined master dataset (Req 1), and separately for the *valid category
  values* of Town/Flat Type/Flat Model/storey_range (Req 3). The validation use is
  intentionally strict.
- **Known gap — Mar–May 2012 are absent from the cleaned data.** HDB published those three
  months in 5-storey bands (`01 TO 05`, …), which the Jan-2012 storey_range domain rejects; that
  one upstream change accounts for 83% of the quarantine bucket. The rule is kept rather than
  "repaired", since 5-storey bands can't be mapped onto 3-storey bands without inventing
  precision. A per-month completeness check (`src/completeness.py`) flags this automatically,
  and the profiling report explains it in full. The other quarantines are genuine values absent
  from Jan 2012: floors above `34 TO 36`, and newer flat models such as DBSS and Type S1/S2.
- **Resale Identifier collisions** are resolved with a deterministic sequence suffix
  (`_01`, `_02`, ...) rather than dropping any row.
- **De-identification uses HMAC-SHA256 with a secret key**, not a plain/salted hash — the
  identifier's construction is simple/enumerable, so a *secret* key (not just a public salt)
  is what actually prevents dictionary/precomputation attacks against it.
